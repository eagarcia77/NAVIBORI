# NAVIBORI merchant and notification audit — 27 October 2026

Scope: merchant registration, account isolation, promotion permissions, nearby offers, and phone notifications. This does not certify unrelated XR modules or hardware compatibility.

## Corrections

- Added authenticated merchant enrollment at `/merchant/register`. A confirmed account can create its own private draft and a merchant membership. Enrollment is idempotent per account/venue; it cannot grant administrative roles, claim another merchant's business, or restore revoked access.
- Provisioned the owner's existing account for venue administration without confirming its email or changing its password. Email confirmation is still required before access.
- Protected merchant identity and review fields in the database. Pending review now freezes profile, hours, catalog, promotion and image writes. Revoked memberships cannot modify those records or image uploads.
- Fixed reviewer read permissions for pending hours/catalog, which previously caused approval to fail. Approved and verified exterior commerce destinations can be published independently of unpublished indoor spatial geometry. The pilot venue's draft status was not changed.
- Isolated local editor drafts by account and business. Prior drafts are archived on account switches, not reused. The console requires a valid session, restores saved profile/catalog/hours, preserves the original business slug, and includes sign-out/account switching.
- Kept nearby coordinates on device; paused GPS watching when the page is hidden; bounded notification frequency to one per offer per day and at least ten minutes between nearby alerts.
- Replaced empty remote pushes with encrypted promotion-specific payloads. The service worker verifies the exact promotion and never substitutes another merchant's offer, including when the selected promotion is beyond the map's two-offer preview limit. Expired/unavailable offers produce a generic directory notice. Notification links stay on NAVIBORI.
- Restricted outbound push destinations to supported browser services; verified subscription state at the backend; required proof of existing subscription keys when recovering a browser installation ID.
- Protected scheduled delivery with a server-only Vault token and a database anti-join so previously sent offers cannot starve new scheduled offers. Manual delivery validates the user's JWT and current merchant ownership/membership in the function body, including when using modern signing keys.
- Added a manual “Enviar aviso general” action for a merchant's own current, verified promotion. It is distinct from nearby-device alerts. Acceptance by a push service does not prove phone receipt.

## Device-test and delivery follow-up

- Added an explicit “Probar en este celular” action after notification activation. It targets only the matching enabled installation/endpoint, reserves an atomic one-minute cooldown, and never broadcasts to other subscribers. A service acceptance message asks the user to check their phone rather than claiming receipt.
- Unsupported browsers now show installation guidance. Returning to the app refreshes notification permission/subscription state.
- Failed, partial and in-progress dispatch records no longer display the misleading “already sent” message. Promotion states refresh with time; expiry is exclusive at the exact end boundary, and invalid intervals fail closed.
- Merchant selection and form fields are disabled while a promotion mutation runs, preventing account/business switching and new text from being lost during a save.
- Long multilingual push payloads are bounded to 3,000 encoded JSON bytes while preserving the promotion ID and safe link. The encrypted payload round-trip also passed for the long-text case.
- `scripts/push-device-test-rollback.sql` passed ownership-match, atomic cooldown and subscription-secret access checks; its fixture was rolled back and no delivery was attempted.
- Live follow-up HTTP checks passed: configuration 200, unregistered test device 404, invalid destination 400, missing manual session 401 and missing scheduler token 401.

To test a real phone: open NAVIBORI, expand the bell settings, activate notifications, then choose **Probar en este celular**. On iPhone/iPad, open NAVIBORI from its Home Screen icon first. The end-to-end receipt remains unverified until the test notification is actually observed on that phone.

## Graphics fallback

Browser inspection found that the absence of WebGL2 caused map setup to fail and replace the whole page with an error. Added component-level error boundaries for the home map and the review location picker. The home fallback keeps directory and merchant-console links available. Reviewers retain the manual verified address/coordinate fields if their graphics picker cannot open. This does not provide a 3D map on unsupported hardware.

## External requirements and verification limits

Google, Microsoft/Azure and Apple OAuth remain disabled until their credentials and callback URLs are configured. They are not advertised as working providers. The owner's email is still unconfirmed; its confirmation was not bypassed.

No real sign-in with those providers, hardware GPS scenario or notification receipt on a phone was tested. No test notifications were sent to real subscriptions. Proximity arrival notifications while the web app is closed still require native geofencing/background-location work. General Web Push is a separate opt-in subscription.

Supabase's remaining Auth advisory concerns leaked-password protection. Review the available account-plan setting at https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection .

## Merchant account recovery follow-up

- Added `/forgot-password` and authenticated `/reset-password`, linked from the login screen. Recovery requests use the existing fixed, owned Auth callback URL. The callback recognizes the pinned Auth SDK's verified PKCE recovery result or a successfully verified recovery OTP; arbitrary redirect targets are ignored.
- Server actions validate matching new passwords and verify the current user through Auth before updating only that user's password. Anonymous and invalid sessions cannot perform the action. Existing sessions remain active after a successful password change.
- Unknown accounts receive the same recovery-request acknowledgement as eligible accounts. Delivery errors are not reported as success. URLs contain only sanitized Spanish messages, never backend diagnostics or submitted passwords.
- Login accepts existing shorter passwords while new signup/reset passwords require at least eight characters. Replaced technical venue wording on the login screen with merchant-facing instructions.
- Validation: 286 tests across 82 files, TypeScript and production build passed. Tests include mocked Auth action/callback integration for expired links, invalid sessions, mismatches, recovery classification, fixed redirect origin and email-service failure.
- No password was changed and no recovery/confirmation email was sent to real users during validation. Actual delivery still depends on SMTP and the user opening a valid email link in the initiating browser. Owner confirmation was checked read-only and remains pending. No OAuth/provider configuration, access roles or database schema was changed.

## Merchant readiness follow-up

- The merchant readiness indicator now uses `ownership_verified` from the current business instead of hard-coding ownership as verified. Only the server-provided publication state displays “Publicado y verificado”; local draft completeness never claims official verification. Pending review has its own label.
- Readiness reads the saved weekly hours and reacts to hours changes, instead of assuming the profile's default opening/closing values prove a schedule exists. Catalog readiness requires a non-empty item title.
- The hours editor starts with closed/unconfigured days rather than invented opening hours. Saving validates all seven unique days and same-day time intervals, reports browser-storage failures and explicitly distinguishes a local draft from account synchronization. Existing valid saved schedules are retained.
- Validation: 289 tests across 83 files and production build (including TypeScript) passed. Added regression coverage for corrupt schedules, duplicate/missing days, invalid time intervals and draft-versus-published labels. No business records, verification fields or permissions were modified.
